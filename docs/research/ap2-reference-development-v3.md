# AP2 original application development v3

This runner replaces the v2 AST subset with imports of all three original AP2
peer applications and the original shopper tool modules. Original task stores,
A2A request handlers, client factories, catalog bodies, checkout creation,
credential association and signing code execute as reached. Original sources
remain unchanged.

Two application interventions are explicit: model responses are bounded offline
catalog/tool-choice fixtures, and HTTPX clients use an owned ASGI transport to
the three local original applications. External transport is refused. A portable
validator for the owned v1 binding helper compares the frozen 136-file original
tree and a fresh installed site-packages inventory; it does not reuse the
Windows native environment qualification claim. The coordinator supplies its
disclosed plain state carrier and fixed development decisions.
The original SDK mandate log destination is redirected to the private temporary
profile so logging cannot write into the frozen source tree.

The first hosted allocation, run 42836579769, installed its Linux environment
successfully and imported the original apps/callers, then stopped before peer
requests when the owned v1 helper compared noncanonical marshal bytes. A
constructed imported docstring case reproduces equal code objects with different
marshal reference encoding. The successor uses a full recursive structural code
fingerprint, including typed constants, bytecode, arguments/flags, closure names,
filename/name, line/position and exception metadata. The unchanged helper retains
its globals, defaults, closure and seven-client-alias guards. Per-callable checks
are retained. Every successor allocation retains its runner, owned helper sources
and all 136 original AP2 source files before import. The failed allocation and
its exact runner copy remain unchanged.

The runner chooses only returned carts and payment aliases, approves the actual
checkout summary, and supplies 123 only when the original public merchant task
requests a challenge. It resumes that merchant task and preserves an actual
failure. It never rescues merchant failure by calling the processor directly.
Original applications generate checkout, token, mandate and receipt values.
No such value is supplied by the offline model fixture.

Provider requests are limited to zero. This is development integration under
interventions. It cannot establish live-provider, native TCP, human-gold,
second-domain or aggregate task qualification.

The hosted workflow uses fresh Linux wheels at the retained Windows runtime's
package versions. Fresh pip download and runtime/module hashes establish the
Linux execution identity. Compiled Windows wheel hashes cannot establish Linux
wheel identity. Private signing files and the runtime environment remain outside
the uploaded artifact. Public verification files are retained.

Local execution applies the existing 1 GiB physical and 2 GiB commit availability
gate. A refusal before original import is retained as a separate result.

Run preparation:

    python -I -S -B scripts/ap2_reference_development_v3.py prepare --output runs/ap2-reference-development/v3/prepared-NEW

Run a bounded development attempt with an explicit installed site-packages:

    python -I -S -B scripts/ap2_reference_development_v3.py execute --output runs/ap2-reference-development/v3/application-NEW --site-packages PATH

The first execution and subsequent fixes are allocated separately. v2 evidence
is preserved unchanged.
