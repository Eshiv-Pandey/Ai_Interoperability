# Finite foundation review

Reviewed 2026-10-24. This is a software review by the separately tasked oracle author. The oracle was authored separately from the baseline and imports none of its validation, predicate or transition code. The reviewer is not an external human reviewer, and reviewing the oracle's own code does not establish a new independent human verification gate.

## Finding and scope

No concrete finite-decision or certificate soundness defect was identified in the inspected code. No code was changed for this review, and no bridge/model calls or new benchmark measurements were made. Inspection covered [the interchange specification](finite-model-v1.md), `src/interoperability/baseline.py`, `oracle.py`, `manifest.py`, `cli.py`, and the crosscheck/trace-integrity tests.

The baseline propagates separate definitely safe and potentially safe frontiers by transition depth. The oracle explicitly explores paths depth first, retains successors after indeterminate invariants, and accepts only paths with a definitely safe prefix. Both check the initial state and permit a zero-transition goal. A definitely unsafe state blocks a path; a false conjunct dominates an indeterminate conjunct. Missing observables differ from explicit null, and boolean/integer equality is type-sensitive. These choices agree with the current abstract specification.

Positive certificate checking reconstructs the path's endpoints and checks every invariant and the final goal. Negative checking reconstructs the entire safe closure at each depth, retains recurrence across layers, and rejects relevant indeterminacy or incomplete evidence. Digest, horizon and validity checks bind the declared manifest. They establish neither authenticity of its source nor realizability of its transitions. Delayed replay certifies the same fixed predicates while the pinned evidence interval is valid; it does not dynamically rewrite literal expiry thresholds.

`tests/test_crosscheck.py` exhaustively enumerates exactly 10,368 worlds: 16 directed two-state edge sets, nine safety assignments, nine goal assignments, four horizons from zero through three, and two completeness assumptions. Each safety/goal assignment is a single equality predicate whose observable is true, false or missing. The tests compare decisions and independently check both conclusive certificates. This enumeration is a finite software crosscheck, not a sampled statistical experiment, a proof for every manifest, or a protocol conformance test. Separate unit tests cover additional operators, type sensitivity and forged certificates.

The development CLI records the exact runtime manifest, declared provenance, evaluation clock, implementation source hashes and actual results. It rejects wire-derived inputs and refuses to overwrite an existing output. Its `certificate_valid` field specifically checks the baseline certificate; the recorded oracle certificate is checked by the crosscheck tests, but not by that CLI code path. CLI agreement counts therefore describe agreement on the supplied authored graphs. The schema's rejection of extra top-level fields does not establish application runtime/gold separation: arbitrary observable names and values still require an independently reviewed projection and contract definition.

## Smallest meaningful wire projection checks

The available development evidence has two distinct bases. `bridge-evidence/a2a-to-mcp-upstream-wire.json` records the pinned upstream author's actual loopback test run and its limits; it is not an independently projected graph. `bridge-evidence/mgcrea-wire-smoke.json` records child-process MCP stdio to loopback A2A exchanges against a deterministic upstream fixture, with zero model calls. Its measured route negotiates MCP `2025-11-25`, uses native task/context IDs, and has no measured MCP task-extension support. The following are proposed projection checks, not claims that they have already passed.

1. **Completed send/get:** derive the outgoing operation from the actual request and the observed state from its paired response. Preserve the peer, native or bridge task namespace, task ID, context ID and response result/error distinction. Verify that send and refreshed get refer to the same task and that the final delivered artifact is present in the captured receiver-visible content. A task acknowledgement, status label or artifact count alone does not establish receipt of the requested result.
2. **Input continuation:** use one captured ask/get-waiting/answer/get-completed sequence. On the measured mgcrea route, the answer is a send with the captured native task ID; do not invent `tasks/update` support. For an independently captured task-extension route, preserve the returned input-request key and requested field when projecting `tasks/update`. The waiting question and answer acknowledgement must fail the completion goal. Completion requires the actual later reply, the same task/context, and the result carrying the supplied answer. The recorded mgcrea answer reply still reports `input_required`; its later refreshed get reports `completed`, so collapsing the answer reply into completion would contradict this trace.
3. **Cancellation:** preserve the cancellation request's task binding and actual returned state. The mgcrea capture includes a peer task with `state='canceled'`, beyond a bare acknowledgement. A cancellation runtime goal may accept that observed state; an ordinary completion goal must not. If testing an acknowledgement-only task-extension response, require a subsequent get before projecting terminal cancellation. The inspected upstream task-extension test source also contains a terminal-task cancel that acknowledges while leaving `completed` unchanged, so an acknowledgement cannot be a generic cancellation-state rule.
4. **Projection rejection and abstention:** use controlled derivatives of captured traces, explicitly labelled mutations, to check mismatched request/response IDs, task/context substitution, removed required observables and omitted outcomes. A projector should reject invalid pairings or preserve missing fields as unknown. Removing an unobserved continuation from a partial trace must not produce `unsupported`. Do not merge separate executions merely because their status labels match; otherwise individually observed edges can create an unrealizable composite witness.

For these checks, retain the source trace hash, exchange positions, projector version/configuration and the predefined runtime contract alongside the projected manifest. Define whether each finite transition represents one request/observed response or a larger explicit macrostep, and use that horizon meaning consistently. Polling can observe asynchronous advancement without causing it; the projection must preserve that observational meaning.

Set `evidence.complete=False` for a graph derived only from these probes. A supported path remains conditional on its observation and realizability assumptions; missing continuations yield unknown. TTL, recipient authority and resource accessibility need explicit measured/configured evidence when required by the contract. Cap evidence validity conservatively or regenerate time-dependent predicates before evaluating later; a past successful retrieval does not establish future accessibility. Neither a successful probe nor baseline/oracle agreement supplies the missing completeness, protocol-fidelity, human-review or novelty gates.
