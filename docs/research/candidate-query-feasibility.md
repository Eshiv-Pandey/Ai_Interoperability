# Query feasibility on the two pinned bridge routes

Prepared **24 October 2026**. **Result: no source-faithful scenario demonstrating the candidate's required 20% observation saving on each bridge has been identified. The screen is impossible on the known-task, one-bundle continuation fragment.** This is a scoped lower-bound result and a negative feasibility observation, not a theorem that every possible application of the bridges admits no improvement. It does not pass the [implementation novelty gate](implementation-novelty-gate.md).

**CP1 remains 5%; novel advantage is not achieved.** The approved 45-day method study, two-bridge scope and novelty objective remain in place. A redesign within that objective is the next research task; this record does not select an applied-only fallback. The user is the sole confirmed researcher. A supervisor review is a potential later human step and has not happened; separately tasked agent source review does not supply that review.

This audit read the [candidate admission specification](candidate-admission-v0.md), novelty gate, actual pinned source and development wire replies. Pins are AmirK-S `58eff9da469bccdc432bf164662727947de646b4` and mgcrea `c4d9d3c57c1746abbf9f6aadd3a9912d464eb1f5`; the unresolved-license Python mapping is not substituted for the audited mgcrea route. The [source index](source-evidence/query-feasibility/source-index.json) stores file hashes, line excerpts and observed query receipts. Its [regenerator](source-evidence/query-feasibility/build_source_index.py) only reads upstream files and writes this local evidence folder. No inference or remote post was used.

## What an actual observation request returns

The unit is one MCP request/response, including every returned fact. Also count downstream A2A/card requests and bytes separately; a bridge's hidden cache or background stream is shared behavior, not a candidate saving. Sending an answer, cancelling or setting webhook state is a task action, not a read-only evidence query. Initialization/profile discovery, cache setup and check time must be charged identically.

| Profile and read-only bundle | Facts available together | Currentness / limit |
| --- | --- | --- |
| Native A2A `GetTask(id, historyLength?)` through the fixture's official SDK | Native task/context IDs, exact task status and its message, returned history and artifact parts. | A task observation when the response is produced. No read grants a lease over future execution or arbitrary linked files. |
| AmirK-S `tools/call(a2a_get_task, {agent, taskHandle, historyLength?})` | The handler resolves the existing handle and checks its agent locally, calls native `GetTask`, and returns exact `a2aState`, mapped `status`, task/context handles, artifact identities, **all returned artifact content blocks**, status-message blocks and requested history in one reply. | Always calls `GetTask` on this generic tool path. Card resolution may incur a separate internal fetch on cold/expired cache. The accepted handle hides native IDs by design; the caller need not independently query them to continue through the same handle. |
| AmirK-S modern `tasks/get({taskId})`, with the declared extension | Task handle, lifecycle state and handle-retention fields; **one `inputRequests.answer` form** when input is required; **the frozen inline CallToolResult** with artifacts when completed. | Refreshes via `GetTask` if nonterminal, no active stream and no recorded bridge error. Active streams feed the record; terminal results are frozen. This is the documented modern task surface, not a universal authoritative reread. No separate `tasks/result` query is mounted. |

## Same-task pending continuation: the honest lower bound

Take the actual common contract: a known returned task on a pinned endpoint must still be waiting for an answer; the caller has the intended answer and must preserve the same task/context binding. Any required current status/question/history/artifact-text information comes from the task read above. The transition skeleton and its completeness are declared separately. A query cannot prove arbitrary future task completion from an API card; the replayable fixture supplies a bounded development transition model.

Let `E` contain the equally supplied profile, caller scope, prior delegation receipt and known task binding. Suppose no accepted current task receipt is available. There are task observations consistent with `E` in which the task is waiting, and others in which it has completed or been cancelled. A zero-query policy receives the same `E` in both cases. It cannot give the correct current binary decision for both; abstaining loses the coverage supplied by a successful task read. Thus any equally sound, equally covering policy needs **at least one** task observation on that unresolved fragment.

One correctly bound task read supplies all those obligations, so the cached/lazy policy attains the lower bound:

```text
Q_min(E) = Q_lazy(E) = 1; Q_candidate(E) >= 1   if a fresh decisive task read is required
Q_min(E) = Q_lazy(E) = 0; Q_candidate(E) >= 0   if accepted evidence is already sufficient
```

This is an information lower bound plus a source-backed attaining policy, not a performance benchmark or a result from an implemented candidate. It applies to request count, not to proving any arbitrary contract from one get. The attaining policy assumes a successful, decisive query at the admission phase; unavailable/unmodeled results retain unknown instead of being converted into a complete negative. It is not a universal bound of one poll from an arbitrary asynchronous submission through completion. If a reply is still working, the continuation contract and its declared bounded model determine whether a supported conditional path exists; if the contract demands completed output now, that reply is insufficient. No private completion time is available to either arm.

If initialization or a required card observation costs `P` requests, equal accounting gives `P+1` to both arms. If the original send response is sufficiently current and includes the obligations required by this contract, both can reuse it. AmirK-S ordinary send often carries the complete pending envelope; mgcrea's early send reply is a summary and can still be `submitted`, so a fresh get is necessary to learn its pending question. If an external contract demands full result contents, mgcrea's summary is insufficient even when terminal. These source differences affect the common lower bound at a phase; they do not authorize giving one arm free evidence.

| Prespecified regime on this fragment | Strong correctly cached/lazy policy | Candidate room to save |
| --- | --- | --- |
| Cold task evidence | One full task read after equally charged setup. | None. Splitting status, binding, history and artifact text into artificial separate probes weakens the comparator. |
| Valid warm evidence | Reuse it; zero new task reads. | None. A saving percentage with a zero denominator is not defined. |
| Changed task/handle binding | Invalidate the old receipt; read the supplied valid new binding once. An invalid/unrecoverable handle leaves unknown under the exposed profile. | None. Neither arm can reuse another task's receipt. |
| Changed relevant task observation | Obtain a full current task read once and recheck. | None under the same change visibility and currentness assumptions. |
| Changed unrelated observation | Keep the valid task receipt and certificate dependencies; no task refresh. | None. Ordinary dependency invalidation already permits this. |
| Expired task evidence | Re-read the same full bundle once if it remains addressable. An actually expired AmirK-S handle is not revived by a query. | None. Evidence expiry and bridge handle expiry must not be conflated. |

For a stream made only of these one-bundle strata, the baseline attains the per-episode lower bound; the candidate cannot save **20% total requests on either bridge**, let alone each bridge. Every obligatory fresh observation must still occur. Extra planner/check overhead has to be counted and cannot produce negative observation cost. This conclusion does not prove impossibility for a pilot whose other contracts actually introduce a richer source-backed observation problem; those contracts must first be located and frozen.

## Artifact access and explicit modern Tasks are different obligations

Inline artifact access is already bundled. AmirK-S maps text/data/raw/URL arms into MCP blocks, retaining artifact metadata. Embedded raw bytes require no new fetch to obtain those bytes. mgcrea deliberately shapes artifact text only; its raw `GetTask` escape hatch restores access to the native part bundle. A comparator must choose that raw bundle immediately when the declared task needs non-text data; first querying the insufficient shaped result and then the raw result is an avoidable policy choice.

An artifact **URL reference** is not the bytes behind the URL and does not establish access by a receiving principal. Neither audited mapping mounts MCP `resources/read`, and AmirK-S explicitly documents resources as undeclared. The fixture's `file` command returns `https://example.invalid/files/report.pdf`; it tests URL-part preservation and does not provide a successful native file dereference. A contract explicitly requiring these bridges' MCP `resources/read` has a documented non-support control under the complete pinned surface. A contract permitting an independent HTTP/file reader needs that real operation, binding and access evidence in its route. A failing reference probe alone does not prove permanent non-support. No external artifact authority/credential/lease was invented to make this case a planner win.

An explicit requirement for modern `io.modelcontextprotocol/tasks` is supported by the AmirK-S **2026-07-28** route's discovery plus per-request client declaration and genuine `tasks/get/update` handlers. `tasks/get` itself supplies the pending form and completed result. Once the pinned profile is already accepted, extension support is a local profile fact; if it is unknown, one discovery is shared by all arms. A generic A2A task tool is not an acceptable replacement when the contract explicitly demands the extension.

The audited mgcrea stdio session negotiated **2025-11-25**, advertised tools and mounted no modern Tasks handlers. Given that complete pinned profile, the explicit modern-Tasks contract is known non-support without task polling. With profile identity unresolved, initialize/read profile evidence or abstain. Repeated task reads cannot establish an absent extension. This is a documented profile difference, not a discovered failure or candidate advantage.

## Richer real dependencies searched before adding complexity

| Actual route dependency | What could require another read | Feasibility consequence |
| --- | --- | --- |
| Endpoint/transport/card selection | A fresh card may be needed when the contract requires current capabilities or the peer endpoint changes. AmirK-S caches cards for one minute and re-resolves clients against the selected interface; mgcrea explicit discovery always refetches and clears the client while ordinary access can reuse cached cards. | These are real cache boundaries. Cache TTL is an implementation policy, **not a provider guarantee that advertised facts stay true**. Cold/changed card cost is shared. No source-backed ordering constraint requiring one baseline to refresh twice was found. |
| Unknown task inventory | mgcrea can list or wait for task IDs before fetching a chosen body; list summaries bundle many tasks. AmirK-S has no generic task-list tool and instead accepts previously returned opaque handles. | A real inventory task changes the input contract. It is not needed for the specified pending task, and does not automatically transfer to both mappings. Strong lazy checkers use the same list bundle and need not read every body. |
| Non-text artifact body | mgcrea shaped output omits raw/data/URL part bodies; raw `GetTask` returns them. | Real projection distinction, but one better query replaces one weaker query. No temporal search problem is induced. The existing fixture/tests already exercise these part kinds; this is not a new natural failure finding. |
| External linked artifact and receiving scope | A real separately owned resource could require task observation followed by native reader access and an actual principal binding. | This is a plausible **route to investigate**, not a realized case on the present fixture. Freeze the real reader and service semantics before any new task is proposed. Serial task-then-resource dependency alone gives every sound arm the same necessary reads. |
| Authorization/extended card | mgcrea has authenticating fetch and a read-only `GetExtendedAgentCard` escape hatch; its summaries omit security fields. AmirK-S explicitly has no authentication in this version. | Existing operations have different applicability. No common principal-specific token/epoch/lease surface was found. A shared-secret local owner must not be promoted into a multi-principal authorization service. |
| Multiple tasks/agents or alternative completion paths | Both can delegate to configured peers, with different alias/ID representations. A user application might require several results or allow alternative successful tasks. | A genuine task DAG could create several bundles and certificate choices. No required cross-task relation of this kind is implemented by the audited fixture's `ask` continuation. Adding arbitrary independent guards or correlations only to favor the planner would be an authored development model; ordinary active decision-region planning is then mandatory prior art. |

The inspected same-task route has `task -> current question -> same-task answer -> result`; the question and identity are returned together, and the answer is a mutation. The additional result read belongs after that mutation. A pre-continuation planner cannot count skipping the post-action result observation as an evidence acquisition advantage while keeping the same result-retrieval contract. The modern stream may publish state between polls; both arms must have the same stream visibility. Unknown future stream completion times cannot be handed to one planner as a deterministic schedule.

## Mechanism comparison and resulting gate decision

The [primary mechanism record](source-evidence/query-feasibility/mechanism-lineage.md) gives paper sections and short verified anchors. These comparisons name overlap; no released comparator was executed in this source audit.

| Closest procedure | What is already established / still required |
| --- | --- |
| Exact reachability with lazy task-cone queries and keyed caching | The same goal cone, bundle contents, stopping certificates and correct dependency invalidation already yield the attaining policy above. Omitting unrelated reads and refreshing affected receipts are standard mechanisms. Every arm must get the same facility. |
| [PC2](https://arxiv.org/html/2610.28484v1), Sections 3.1, 3.3-3.4, Appendix A | Combines sources in a visible view and checks obligations across hidden compatible states and bounded intervening control steps. Its per-call universal preservation differs from existential bounded route completion. That difference is a scope distinction; a common-fragment observation/cost comparison is needed for superiority. Real bridge timestamps do not supply PC2's mediation/fidelity assumptions. |
| [EC2](https://papers.nips.cc/paper_files/paper/2010/file/1e6e0a04d20f50967c64dac2d639a577-Paper.pdf), Sections 2-4 | Selects costly observations until a decision class is identified, with nonuniform costs and modeled correlated noise. Expected-cost guarantees under a prior do not transfer to v0 minimax planning. Disallowing correlations or forcing exact-hypothesis identification would weaken this comparator. |
| [HEC](https://proceedings.mlr.press/v33/javdani14.pdf), Sections 2-3 | Handles overlapping successful decision regions: alternate supported certificates need not form disjoint labels. Static deterministic hypotheses do not directly implement receipt expiry, so use a labeled adaptation with matched semantics and costs. The lack of static expiry support alone does not demonstrate a new algorithm. |
| [Finite contingent planning](https://ojs.aaai.org/index.php/AAAI/article/download/8365/8224), contingent-planning model on p.1757 | A query choice is an OR node and every allowed response is an AND branch. Finite receipts, time and remaining budget form an ordinary expanded state. The v0 `min(cost + max(successor value))` recurrence is a finite dynamic program, not a new recurrence. |

**Decision:** retain this lower-bound/null evidence; do not manufacture separate status/artifact queries, delays, private future schedules, unknown authority services or validity TTLs to satisfy the candidate screen. The current candidate has no demonstrated temporal query advantage, and passing it on authored graphs would not resolve G1/G4. A subsequent redesign must identify a required real dependency or useful representation/procedure beyond these techniques, preserve both bridges and all authorized research dimensions, and state a fair achievable efficacy screen before measurement. Scope or contribution-route changes remain explicit decisions; none is made here.
