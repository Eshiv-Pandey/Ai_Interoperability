# Alternate original AP2 bridge-profile source review

11 November 2026. Source eligibility only: retained files/history plus read-only GitHub metadata and immutable source URLs. No bridge/application execution, model calls, experiments, Git mutation, source modification, run allocations or dispatch. Only this new review document was created.

**Result: no full-scope eligible alternate was found in the inspected source set.** One independent bridge has a concrete A2A 0.3 profile, but its original payload mapping cannot carry AP2's required fields. The two independent-route requirement and complete human-present payment/OTP/receipt scope remain open. This finite search does not establish that no suitable bridge exists anywhere.

## Required original boundary

AP2 pin remains `e1ea56db72a6385bce3e5c1112b3a56ce60acb43`, Python A2A SDK `0.3.24`. Preserve original prefix-scoped cards, legacy `message/send` and `tasks/get`, `X-A2A-Extensions: https://github.com/google-agentic-commerce/ap2/v1`, routing TextParts, actual top-level AP2 DataParts, and the original task/context IDs through OTP and receipt.

The original executor separates text/data parts and routes using its first text (`runs/ap2-environment-preparation/source-stage-v1/ap2/code/samples/python/src/common/base_server_executor.py:134-147,164-169`). `common/message_utils.py:22-38` searches each data dictionary directly for the named key. The processor reads the direct PaymentMandate, checkout hash and `challenge_response` keys (`roles/merchant_payment_processor_agent/tools.py:53-80`). A `{skillId,args:{...}}` envelope or JSON inside text cannot satisfy those reads.

## Consequence for continuation work

The concrete SDK0.3.13 skillmap profile is useful evidence that legacy discovery, configurable headers and task reads can coexist in an independent bridge. It does not supply original AP2 data routing. It also loses the server-returned context: `dispatcher.ts:199-215` returns only the task ID/status text, and `invocation-runtime.ts:383-388` creates a running record using a caller context or a fresh UUID. An input-required Task remains a running handle, while the same-session running guard rejects the next invocation. These are source blockers to original same-task OTP continuation, beyond the nested-payload blocker.

Forwarding its nested `args`, adding an unwrap layer, replacing its dispatcher through an injection API, rewriting cards or adding owned transport shims would create a disclosed different route. None is an unchanged original bridge repair.

No eligible pair can therefore be frozen from this inspected set. Keep the existing route failures and full-scope gates visible; obtain another implementation with an original public mixed-part/direct-data API and extension-header configuration, or an upstream original compatible release, before source-preserving two-route experiments become eligible. Source review alone supplies no runtime or scientific gate credit.
