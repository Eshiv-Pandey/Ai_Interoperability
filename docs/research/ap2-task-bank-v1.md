## Closed schema and separation

The two JSON files have the same closed top-level keys: `schema_version`, `domain`, `source_pin`, `authorship`, `qualification`, `records`. Schema version is `source-task-bank/1`. `source_pin` is an object identifying the AP2 repository/commit/retained root and separate pinned A2A SDK source. Every record inherits the top-level authorship and qualification flags.

`application.json` records have exactly `id`, `split`, `template_family`, `distinct_obligation`, `public`. The `public` object contains `task`, `prompt`, `fixture_recipe`. Its documented domain-specific recipe fields are `execution_class`, `fixture_origin`, `source_compatible_setup`, `public_choices`, `steps`, `capture_public_surfaces`, `realization`. They are prospective operator recipes and public human choices; they contain no materialized private task IDs, valid token bytes, live receipts, gold objects, reset plan or reference trajectory.

`evaluator.json` joins by those same four common record fields and adds exactly `expected_facts`, `expected_order`, `expected_state`, `reset`, `legitimate_alternatives`, `near_misses`, `source_refs`, `review_status`. The six expectation/alternative/control fields are arrays of `{claim, source_refs, status}` objects. Status is `source_supported` or `pending_human_judgment`. Every source-supported claim cites at least one key in its own record's `source_refs`. Each citation value is `{path, sha256, lines: [inclusive_start, inclusive_end], symbol}`. `review_status` is `not_reviewed` for every record.

`source_supported` means a source inspection supports the stated code relation; it does not mean independently reviewed gold, validated evidence provenance, observed execution or a satisfied task. Evaluator policy, semantic intent, full reset, uncertain association and success-credit decisions remain explicitly `pending_human_judgment`. Authored expected-order text is a target specification, not an actual reference trajectory.

All public prompts/recipe inputs can be released to the task actor. Evaluator files, exact gold facts/order/state, reset checks, alternatives, near misses and citation matrices must stay out of actor context during future scored execution. Reviewers may inspect both sides; that review access is separate from actor input.

## Required source semantics in evaluation

The first processor payment call verifies its supplied mandate and raises an actual OTP DataPart challenge with `input_required`. Merchant status forwarding preserves the processor status Message, including child identity. The shopper OTP tool binds its saved merchant task ID/context; merchant child mapping scans history forwards and takes the first differing task ID, without origin/role/nonempty filtering. Retain the full original history and the value actually selected. Never replace that heuristic with an idealized mapping in gold or infer identity from RPC/session/path labels.

The original shopper checks state `challenge`/`task.status.challenge`, whereas the processor publishes `input_required` with challenge data in `task.status.message`. Preserve this source compatibility gap. Generic `Status: input_required` does not prove the model requested or received human OTP input. A human-authored diagnostic reply or direct child endpoint control must be labelled separately and cannot upgrade the original shopper prefix.

The wrong string OTP branch remains input-required and publishes incorrect-response text; it need not repeat the original challenge DataPart. Exact `123` selects completion but does not guarantee it: signature verification, credential lookup/state/artifacts and receipt delivery can fail. Correct-OTP failure and completed-but-empty credential output remain unmet completion targets. Registered raw-credential handling means empty artifacts are contingent, not inevitable.

The credential provider binds the most recent unbound token to a signed transaction without an explicit user/token/task argument. Public source account/token helpers can support separately labelled ordering controls, but cross-account card eligibility, native outcomes and intended-user association require review. Never advertise a code-reading adverse case as an observed exploit or qualified original purchase.

A changed independently valid mandate on a pending task can have a source-consistent reference to its current supplied leaf. The inspected pending-task branch does not establish rejection of changed valid mandates. With no explicit contrary human intent, original transaction/credential association stays UNKNOWN. With independent explicit confirmation for a different transaction, an authored near miss can fail the intended-task semantic obligation separately from unobserved upstream acceptance/rejection. Valid alternatives must be created by original signer/helpers, not invented JWT strings.

Exact source receipt-reference semantics are:

```text
leaf = presentation.rsplit('~~', 1)[-1].split('~', 1)[0]
reference = unpadded_base64url(SHA256(UTF8(leaf)))
```

Whole-presentation equality, closed-leaf equality and receipt-reference equality are separate. A payload-JSON hash, padded base64, whole-presentation hash or computed hash of malformed/empty input is not authentication or source-reference equivalence.

Receipt extraction uses actual DataParts under `ap2.PaymentReceipt`. `only` rejects empty/multiple lists; equal duplicate receipt objects in one final artifact collection are still ambiguous, while repeated snapshots of one receipt do not create independent receipts. Missing final observations stay unknown; fully observed missing/malformed/conflicting receipts cannot receive an unambiguous receipt pass.

Success/Error schema declarations differ from original Success constructor obligations. Keep empty `iss`, explicit null optional fields and allowed generated declarations intact. The Success constructor uses one fresh UUID hex string for payment/PSP/network identifiers. Strict JSON observer rules such as rejecting boolean `iat` and comparing all supplied extra fields are declared evaluator policy, pending review; they must not be described as exact upstream Pydantic acceptance/normalization equivalence. Extra fields are not explicitly forbidden by the generated models and can be omitted by original validation/model dumping.

The public source receipts and credentials are synthetic demo semantics. Provider receipt handling is a no-op acknowledgment. No real debit, durable order/rollback ledger or exactly-once mutation is inferred, and no extra real-bank-ledger eligibility gate is imposed on the declared simulated domain.
