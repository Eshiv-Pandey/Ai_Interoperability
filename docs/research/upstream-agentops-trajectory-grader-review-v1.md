## Preserve the exact configured metric

`evals/test_config.json` configures only `tool_trajectory_avg_score`, threshold `1.0`, match type `IN_ORDER`, with `evals.required_trajectory.evaluate_required_tool_trajectory`. It configures no answer-match, schema, response-facts, grounding or judge metric. Reproducing this metric means reproducing its actual algorithm, including its permissive cases.

`required_trajectory.py:21-67` implements an ordered subsequence over the flattened actual function calls. Each required call consumes a later matching actual call with the same name and recursively matching required argument subset. Extra calls before, between and after required calls are allowed; the algorithm does not reject an extra write. Extra actual mapping keys are allowed. Required lists must have exactly the same length and match positionally. Boolean comparison requires identical types. Other scalar comparison uses Python equality. An expected empty string permits an omitted mapping key, reflecting an empty function default, but does not permit a supplied nonempty value. Call argument values are fed as `actual.args or {}` and `expected.args or {}`.

The adapter at `required_trajectory.py:81-130` requires equal actual/expected invocation counts. It assigns `0.0` or `1.0` per invocation and averages those values; status uses `score >= threshold`. Missing expected invocations or count mismatch is an error, not an invented score. Do not substitute an exact-call-list comparison, demand identical argument dictionaries, forbid extras, sort by IDs, deduplicate by call IDs, require tool success, or require a successful reply between calls when reporting this original metric.

The installed accumulation path matters. `evaluation_generator.py:675-692` emits every original runner event and adds a synthetic user event at the first observed invocation. The non-live generation path appends yielded events at `942-947`. Grouping at `1141-1156` preserves list order by invocation ID. `convert_events_to_eval_invocations:1003-1066` selects content-bearing calls, responses, text, inline data or grounding metadata without a partial-event filter. It keeps final-event content when it includes a function call; otherwise final text is represented separately. `eval_case.get_all_tool_calls:220-244` returns legacy `IntermediateData.tool_uses`, or scans `InvocationEvents` in event order then part order and appends each function call. It checks neither response identities nor successful execution and performs no partial-call deduplication.

Consequently, ordered function-call parts in the **same original event** can satisfy the configured metric, even though they are a batch and do not witness awaited dependencies. Repeated function calls carried by partial events remain in the accumulated sequence. A recorder/reconstructor must preserve those events and boundaries, then expose a separate flat sequence compatible with this source algorithm. Capturing only nonpartial database rows or final A2A task artifacts cannot establish equivalence to the SDK's complete event accumulation.

## Stronger checks must preserve source behavior and uncertainty

Treat an expected missing-entity error as a matched observation. Treat a missing response, runtime failure or missing log evidence as unavailable evidence; do not convert it into successful facts from the reference answer.

Data dependencies are application/prompt requirements (`composition.py:37-44`, `tools.py:65-68`, `report.py:40-43`, `workflow.py:65-72`). A stronger order witness needs invocation/session/branch association, original event and part boundaries, call/response identity, and an earlier successful response containing the consumed service or runbook. Parts in one function-call event are a batch. A later matching response does not retroactively prove its values were available to an earlier call. Unknown IDs, repeated confirmation phases, ambiguous pairing, missing replies, or equal/inadequate timestamps remain unresolved. Keep original source call-array order for the metric while reporting these limitations separately.

## Passive original-event recorder feasibility

The original `create_app` constructs `_SessionSerializingRunner` at `server.py:564-574`, passes that exact runner to `to_a2a` at `601`, and exposes it at **`app.state.runtime.runner` (`608`)**. A class-wide monkeypatch is unnecessary. A scoped observer may retain the original bound instance `run_async` and attach an instance-specific delegating async generator before any request begins. This is an instrumentation proposal, not an implementation or verified transparent wrapper.

The original `_SessionSerializingRunner.run_async:184-211` holds its session-invocation gate and delegates to `super().run_async` under `contextlib.aclosing`. The observer must call that bound original method once with unchanged arguments, preserve its yielded order and the exact yielded Event objects, and wrap its iterator in `aclosing` too. The active executor already uses `Aclosing(runner.run_async(...))`; the installed `Aclosing` is the stdlib `aclosing` alias. Closing or canceling the outer wrapper must close the original generator so its session locks and the original lifespan can clean up. Original exceptions and cancellation must propagate; the recorder must not retry the generator or suppress an original error. The observed executor uses async iteration and close; arbitrary `asend`/`athrow` transparency beyond that consumed interface is not established.

The active path is source-selected: `server._agent_executor:347-359` sets `force_new_version=True`; `a2a_agent_executor.py:127-137` selects the maintained implementation. `a2a_agent_executor_impl.py:193-204` consumes the Event and then applies `LongRunningFunctions.process_event`; only afterwards does it convert/enqueue at `206-223`. `long_running_functions.py:52-88` deep-copies the Event and removes flagged function calls and responses from normal parts, collecting them for later input-required publication (`90-113`, executor `225-237`). Thus a snapshot taken synchronously in the delegator immediately **before yielding the original Event** observes those parts before deferral. A converter `after_event` interceptor is too late for complete predeferral content.

Snapshot immutable bytes at that point, not a retained mutable Event reference serialized later. Preserve a declared serialization shape for the full Event, including original call/response IDs, content-part positions, `partial`, long-running IDs, invocation/author/branch/node metadata, actions/state deltas, errors and other model fields. Opaque internal fields may be retained without relying on undocumented semantics. The snapshot is the original runner's post-policy event, not unprocessed provider tokens or pre-tool-guard data: the base runner invokes plugin callbacks and appends nonpartial events before yielding (`runners.py:1453-1477`). Partial events can exist in the stream without corresponding nonpartial database rows.

A bounded **fail-open journal** is appropriate for passive observation: if snapshot serialization or recorder storage fails, retain an explicit gap/error flag when possible, mark event-stream evidence partial and continue yielding the same original Event. Do not fabricate a row or let an observer error replace an application response. Allocate monotonic local sequence numbers at observation, associate them with bound native invocation/session information, and disclose byte/event/queue limits and any overflow. If later asynchronous writing is used, enqueue already immutable bytes before the yield and close/drain only the recorder's own resources during original owned shutdown. A complete journal needs a successful terminal/drain receipt as well as no recorded gap; prefix rows alone do not prove complete execution.

Snapshot work and bounded journal writes add latency; no source-text review can prove zero timing perturbation. The recorder must not make model calls, alter tool/model/configuration surfaces, add approval, rewrite Event content, modify source archives, or use evaluator expected answers as runtime input. A new versioned observer and bootstrap integration would need its own source identity and focused software validation before any native use. This review does not authorize editing the already frozen modules or claim that the proposed recorder has been installed.
